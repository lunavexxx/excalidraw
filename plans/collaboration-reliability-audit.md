# 多人协作链路检查

日期：2026-10-09。范围：仓库实现与本地回归测试；未取得出现提示的部署环境日志，不能据此认定线上断线的具体原因。

## 当前链路

浏览器进入服务端画布后自动建立 WebSocket，握手刷新 JWT，`join-room` 经 API 校验画布权限。编辑立即应用在本地；元素增量发送到 room 服务，经 PostgreSQL `canvas_events` 持久化后，携带 seq 通过 Socket.IO Redis adapter 广播到同一画布的其他连接。发送者收到持久化确认。其他 room 实例通过 Redis Pub/Sub 接收广播。

重连后按游标请求 `sync-request` 补丁，失败时回退 HTTP 场景快照；本地和远端按元素版本合并，再补发当前场景。服务端按元素 id、version、versionNonce 确定胜出状态，支持重复和乱序合并；客户端另有编辑中保护，不宜将整套实现直接称为严格 CRDT。

在线名册通过 Redis adapter 的跨实例 `FetchSockets` 汇总。成员状态、鼠标与编辑持久化是不同通道。广播范围应为已授权加入相同画布的用户。

## 本次修复

- 入房确认从跨实例名册查询中移出。过去 Redis 查询失败直接返回，没有入房回执，已授权的编辑者也无法完成初始化。
- 客户端入房确认增加 10 秒超时，超时重新握手；旧连接的回执不影响新连接。
- 编辑持久化确认增加 5 秒超时，缺失回执走现有失败恢复路径。补拉场景后重置阻挡待补发编辑的场景版本标记，允许后续巡检重试。
- 空增量不发送，避免服务端拒绝空帧导致无意义的确认超时。
- 场景巡检同时补拉在线名册；仅收到实际名册后标记在线状态可用，入房和权限回执不再代表名册可用。

巡检沿用现有 120 秒周期，因此确认失败后的重试仍可能等待下一轮。此轮修复没有引入新的协议或消息存储。

## 与预期仍有的差距

1. **Redis 当前是 Pub/Sub，不是可重放队列。** 跨实例实时广播已有，但 Redis 订阅中断期间的帧不能由 Pub/Sub 重放，当前靠数据库补丁恢复。
2. **缺少按画布隔离的持久化客户端 outbox。** 协作期间暂停普通本地保存，待发送编辑主要在当前页面内存中。继续编辑和重连补发已有，刷新或关闭页面后可靠恢复尚未完整实现。
3. **数据库故障阻塞实时编辑广播。** 当前先落库后转发，未获持久化确认不能当作已保存；room 内存队列不是可靠消息存储。
4. **在线名册与编辑同步需要独立状态。** 不能将真实断线标成在线。产品承诺应是“编辑始终可用，网络恢复后自动同步”，同时准确展示同步状态和待发送状态。

## 若采用 Redis 队列的实施要求

建议使用 Redis Streams 保存可重放编辑事件，并为事件提供稳定的 event_id、画布 id 和客户端操作标识。服务端仅在可靠写入成功后确认接收，客户端确认前保留 IndexedDB outbox，重复发送按标识去重。

每个 room 实例必须独立消费广播事件，向本机相应房间的已授权连接投递。所有 room 共享同一 consumer group 会分摊消息，无法保证每个实例都收到；需要独立消费游标或每实例独立 group，并定义退出实例的清理策略。数据库投影可由另外的消费组处理，接收确认和持久化进度要有明确语义。

Streams 的保存长度、过期、回放起点和快照游标必须一起设计；超出保留窗口的客户端先拉快照，再补发自身 outbox。鼠标等瞬时消息无需可靠队列。不要将 Redis Stream ID 直接混用为现有 PostgreSQL seq。

## 验证与部署核查

本地验证：room Go 测试；前端 Portal、自动入房 hook 与协作回归测试；TypeScript 与变更文件格式检查。

部署还需检查浏览器 WebSocket 握手、`connect_error` 与断开原因，Caddy `/socket.io/` 路由，room 的 JWT/内部 API 配置，Redis 连通性和 `fetchSockets` 日志。现有 `apps/room/e2e/multi-instance.mjs` 可验证跨实例名册与广播；此轮没有运行真实 Redis、数据库和双实例联调。

后续验收应覆盖：两个 room 实例互传、断网继续编辑与重连合并、断网后刷新恢复、重复投递、Redis/数据库重启、名册故障不阻塞编辑，以及重连时权限被撤销或降为只读。
